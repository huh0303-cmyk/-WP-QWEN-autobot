## 0. 왜 4단계로 단순화하는가

업로드된 콘솔은 이미 4단계로 나뉘어 있었다: Research/Title Agent → Writer
Agent → Main Review Agent → Image Worker, 그 뒤에 발행. 이번 통합에서는
Main Review를 별도 Agent로 두지 않고 **Writing Agent 안의 자체 검수 단계로
흡수**한다. Agent가 많을수록 실패 지점(각 Agent 간 핸드오프, 토큰 낭비,
타임아웃)이 늘어난다는 게 지금까지 24개 WP + 33개 Blogspot 운영에서 반복
확인된 사실이기 때문이다.

**최종 4단계:**

```
1. 키워드/주제 리서치 Agent
        ↓
2. 글쓰기 Agent (자체 검수 포함)
        ↓
3. 이미지 Agent
        ↓
4. 발행 Agent (플랫폼별 카테고리 매핑 포함)
```

이 4단계는 WordPress, Blogspot, Tistory, Naver **네 플랫폼 전부에 동일하게**
적용한다. 플랫폼마다 다른 것은 4번(발행) 단계의 로그인/에디터/카테고리
매핑뿐이고, 1~3번은 플랫폼과 무관하게 동일한 산출물(제목, 본문, 태그, 이미지)을
만든다. 즉 **콘텐츠는 한 번 만들고, 발행 어댑터만 플랫폼별로 갈아 끼운다.**

## 1. 페르소나 & 톤앤매너 — 사이트별 1페르소나 고정

원칙: **사이트/블로그 1개 = 페르소나 1개 = 고정.** 매 글마다 페르소나를 새로
생성하지 않는다 (업로드된 콘솔의 계정별 `imageStylePrompt`, `preferredTone`
저장 방식과 동일한 사고방식).

각 사이트/계정 등록 시 아래 4개 필드를 **1회 고정**하고 이후 모든 글쓰기
Agent 호출에 그대로 주입한다:

| 필드 | 예시 | 비고 |
|---|---|---|
| `persona` | "10년차 부동산 실무자가 정리해주는 톤" | 가짜 전문가 행세 금지 — `docs/GITHUB_...` 정책과 동일하게 허위 자격 사칭 금지 |
| `preferredTone` | "담백하고 단정적, 과장 없음" | |
| `publishPurpose` | "신청 전 확인 체크리스트 제공" | 글의 목적을 명시해야 Writing Agent가 클릭베이트로 새지 않음 |
| `excludedTopics` | "투자 추천, 특정 종목 언급" | 리스크 있는 주제 사전 차단 |

**톤앤매너 공통 금지어/금지 패턴** (`automation_hub/editorial_language_policy.py`
정책을 전 플랫폼 공통 최소 기준으로 승격):
- "Unlock/Unleash/Ultimate Guide/모든 것/총정리/궁극의 가이드" 류 AI 클리셰 제목 금지
- "in today's fast-paced world / 끊임없이 변화하는 시대에" 류 AI 클리셰 도입부 금지
- 제목이 "How"로만 시작하는 뻔한 패턴 지양
- 허위 전문가 인격 생성 금지 (의료·법률·금융처럼 자격이 문제되는 카테고리는
  `automation_hub/medical_editorial.py`식 카테고리별 편집 정책을 우선 적용)

## 2. 이미지 정책 (전 플랫폼 공통)

기존 `docs/LONDON_PROJECT_CONTENT_PIPELINES.md` 3절의 순서를 그대로 따르되,
업로드된 콘솔의 "계정별 이미지 스타일 고정" 개념을 추가한다:

1. Pexels / Pixabay 등 저작권 안전 무료 이미지 우선
2. 무료 이미지 없으면 SDXL Lightning
3. 실패 시 FLUX Schnell
4. 전부 실패하면 무이미지 허용(이미지 때문에 발행 자체를 막지 않음)

**추가 규칙:**
- 계정/사이트별 `imageStylePrompt`를 1회 등록해서 타이틀 이미지·본문 이미지가
  같은 사이트 안에서 시각적으로 일관되게 한다.
- 타이틀 이미지 1장 + 본문 이미지 N장(사이트별 `maxBodyImages` 설정)을
  Writing Agent가 아니라 **별도 이미지 Agent**가 만든다 — 글쓰기와 이미지
  생성을 한 프롬프트에 섞으면 둘 다 품질이 떨어진다는 게 콘솔 운영에서
  확인된 실패 패턴.
- 뉴스/시사 카테고리는 타 언론사 사진 무단 사용 금지, 원 출처 허용 이미지·
  퍼블릭도메인·명시적 라이선스 이미지만 사용.

## 3. 4-Agent 상세 스펙

### Agent 1 — 키워드/주제 리서치

**입력**: 사이트 프로필(카테고리, 키워드, `excludedTopics`, `freshnessLevel`,
`searchChannel`, `topicMode`)

**동작**:
1. `topicMode=manual`이면 지정 주제 그대로 사용, `auto`면 카테고리+키워드로
   주제를 스스로 고른다.
2. 신청/모집/지원금/법률/가격/일정처럼 **독자 행동에 직접 영향을 주는 주제는
   공식·기관 출처를 우선 검색**한다(정부/공공기관/공식 홈페이지).
3. AI·기술·시장 동향처럼 발표형 주제는 블로그 후보만으로 확정하지 않고
   독립 편집 매체 또는 신뢰 가능한 웹 근거를 최소 1개 이상 확인한다.
4. 검색 후보 품질을 점수화한다 — "발췌 120자 이상 또는 본문 300자 이상"을
   최소 기준으로 하고, 기준 미달이면 `insufficient` 상태로 다음 단계에
   경고를 넘긴다(콘솔의 `summarizeSourceQuality` 로직과 동일).
5. 제목 후보를 2~3개 뽑아서 과거 발행 제목과 임베딩 코사인 유사도를 비교한다
   — **0.75 이상이면 중복으로 판단, 재시도**(콘솔의 실측 임계값을 그대로
   채택).

**출력**: 확정 주제, 확정 제목, 근거 자료 리스트, source_quality 상태

**실패 처리**: 근거 자료가 `insufficient`면 이 단계에서 멈추고 사유를 남긴다.
근거 없이 다음 단계로 넘기지 않는다 — "완료" 문구로 넘어가는 게 아니라
`status: failed, failurePhase: research`로 명시적으로 실패 처리한다.

---

### Agent 2 — 글쓰기 (자체 검수 포함)

**입력**: Agent 1의 확정 제목 + 근거 자료 + 사이트 페르소나/톤/목적/금지어

**동작**:
1. 본문, 태그, 이미지 프롬프트(타이틀 1개 + 본문 N개)를 함께 작성한다.
2. 자체 검수 체크리스트 (콘솔의 "Main Review Agent" 역할을 이 단계로 흡수):
   - 제목-본문 일치 여부
   - 근거 신뢰도 (Agent 1이 넘긴 출처와 실제 인용이 맞는지)
   - 클리셰 패턴 재검사 (1절의 금지어 정규식)
   - 독자 행동 유도 문장이 있는데 근거가 없는 경우 삭제
   - 현재성 — "현재/최근/올해" 같은 표현을 쓸 때 실제 날짜와 모순 없는지
3. 태그 생성: 특수문자 제거, 중복 제거, 최대 29개로 제한(Naver 태그 제한
   기준을 전 플랫폼 공통 상한으로 채택 — Tistory/WP/Blogspot도 이 이하로
   맞추면 안전).

**출력**: 최종 제목, 본문, 태그 배열, 이미지 프롬프트 배열

**실패 처리**: 검수 체크리스트 미달 시 최대 1회 자체 재작성 후에도 실패하면
`failed`로 종료 — 품질 미달 글을 "일단 발행"하지 않는다.

---

### Agent 3 — 이미지

**입력**: Agent 2가 넘긴 이미지 프롬프트 + 사이트별 `imageStylePrompt` +
`titleImageAspectRatio` / `bodyImageAspectRatio`

**동작**: 2절 이미지 정책 순서(무료 이미지 → SDXL Lightning → FLUX Schnell
→ 무이미지)대로 생성/수집. 타이틀 이미지 1장, 본문 이미지는 사이트별
`maxBodyImages` 설정 수만큼.

**출력**: 타이틀 이미지 파일 경로, 본문 이미지 파일 경로 배열(순번 포함)

**실패 처리**: 이미지 실패는 발행을 막지 않는다(무이미지 허용). 단, 실패
사유는 로그에 남긴다.

---

### Agent 4 — 발행 (플랫폼별 어댑터 + 카테고리 매핑)

Agent 1~3의 산출물은 플랫폼과 무관하게 동일하다. 발행 Agent는 대상
플랫폼에 맞는 **어댑터**만 바꿔 낀다.

| 플랫폼 | 로그인 방식 | 세션 유지 | 카테고리 매핑 | 비고 |
|---|---|---|---|---|
| WordPress (24개) | REST API + Application Password | 불필요(API) | 사이트별 카테고리 자동 매칭(3단계 매칭 로직 기존 유지) | GitHub Actions에서 직접 호출, 브라우저 불필요 |
| Blogspot (33개) | Google OAuth (Blogger API) | 리프레시 토큰 | 사이트별 카테고리/라벨 매핑 | API 기반, 브라우저 불필요 |
| Tistory | Kakao 계정 브라우저 로그인 | **전용 Chrome 프로필에 세션 저장·재사용** | 카테고리 드롭다운 선택 | TinyMCE 에디터 자동화 필요 |
| Naver Blog | **수동 로그인 전용**(자동입력 절대 금지) | **전용 Chrome 프로필에 세션 저장·재사용** | 카테고리 드롭다운 선택 | 보안확인(CAPTCHA) 발생 시 사람이 직접 입력 |

**Naver/Tistory 확장 시 반드시 지킬 안정화 규칙** (업로드된 콘솔에서 실제
검증된 부분 — 이게 이번 지침의 핵심):

1. **아이디·비밀번호를 코드가 절대 입력하지 않는다.** 계정에는 Blog ID만
   저장하고, 로그인 화면이 뜨면 사람이 그 Chrome 창에서 직접 입력한다.
   이유: 자동 로그인은 네이버/카카오 어뷰징 탐지에 걸려 계정 정지로
   이어질 위험이 실제로 있고, 콘솔 개발 과정에서 이 원칙 때문에 로그인
   자동화 코드 자체를 아예 제거했다.
2. **로그인 세션은 계정 전용 브라우저 프로필 디렉터리에 저장**하고 이후
   작업은 그 프로필을 재사용한다. 매번 새 프로필로 로그인하면 보안확인이
   매번 뜬다.
3. **보안확인(CAPTCHA) 화면과 로그인 필요 화면을 구분**해서 처리한다.
   - 보안확인만 뜬 경우: 사람이 풀 때까지 대기(타임아웃 있음), 풀리면
     원래 작업 이어감.
   - 진짜 로그인 필요(세션 만료)로 판정된 경우: `SESSION_EXPIRED`로
     명확히 구분해서 보고 — "보안확인 타임아웃"과 "세션 만료"를 같은
     오류로 뭉뚱그리지 않는다.
   - 글쓰기 도중에 보안확인이 뜨면 브라우저를 닫고 처음부터 다시 하지
     않고, **같은 브라우저 안에서 재시도**한다(작성 중이던 초안을 살리는
     Naver 임시저장 이어쓰기 포함).
4. **Naver 발행 성공 후에만 같은 제목/본문/이미지/카테고리/태그를 Tistory에
   미러링**한다. Naver가 실패했는데 Tistory만 발행되는 순서 역전을 만들지
   않는다(콘솔의 기본 흐름 그대로 채택 — 순서를 강제하는 이유는 Naver가
   더 엄격한 근거 검증을 통과한 콘텐츠라는 걸 확인하는 게이트 역할을
   하기 때문).
5. **Tistory/Naver 세션은 발행 전 별도 세션 점검 단계를 먼저 실행**한다
   (콘솔의 `checkNaverSession` / `checkTistorySession`과 동일). 세션이
   무효인 걸 발행 도중에 알게 되면 이미지 업로드 등 중간 산출물이
   낭비된다.

**출력**: 발행 URL/게시물 ID, 발행 상태

**실패 처리**: 발행 실패는 재시도 정책을 따른다 —
- `duplicate_retry`(제목 중복): 같은 대상으로 즉시 재시도, 최대 3회
- `research`/`failed`(근거 부족): 같은 대상 반복 재시도 금지, 다음
  스케줄로 넘김
- `SESSION_EXPIRED`: 자동 재시도 금지, 사람의 로그인 조치 필요 상태로 대기

## 4. 사이트/블로그 등록 시 최소 필수 필드 (신규 등록 체크리스트)

이게 없으면 4-Agent 파이프라인이 "추측"으로 채워 넣게 되고, 그게 반복 실패의
원인이다.
