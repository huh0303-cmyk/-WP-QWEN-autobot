# Universal Affiliate Engine — Implementation Specification
Date: 2026-10-31 (KST)
Status: DESIGN BASELINE — implementation not yet deployed
Repository: huh0303-cmyk/-WP-QWEN-autobot

## 1. Goal
Build one provider-agnostic affiliate publishing engine for the London Project. It must support shopping, travel, hotels, activities, transport, eSIM and other approved affiliate categories through replaceable provider adapters. Do not hard-code Coupang or any travel provider into the publishing workflow.

## 2. Provider model
Initial adapter registry:
- Coupang Partners — shopping/products (Korea)
- Trip.com Affiliate — hotels, flights, trains, activities and travel products, subject to the account's approved inventory and terms
- Agoda Affiliate — accommodation
- Booking.com Affiliate — accommodation/travel, only if the account is approved
- Extensible adapters: other hotel, OTA, tour, eSIM, transport and commerce programs.

Each provider adapter must declare:
- provider_id, display_name, program_type, supported_categories, supported_markets, currency
- link_mode: approved deep link / approved API / approved feed / manually supplied tracking URL
- credentials_ref (secret name only; never secret value)
- approval_status: unknown / pending / approved / rejected / paused
- terms_url, image_policy, attribution/disclosure requirements
- tracking/sub_id support and reporting capability
- active flag and last_verified_at.

Do not represent a provider as connected, approved or revenue-attributing until verified from its dashboard or API.

## 3. Core data model
### Content target
site_url, post_id, permalink, title, excerpt/topic, language, category, published_at, views, views_source, views_period, status.

### Offer
offer_id, provider_id, external_item_id, title, category, destination/market, price, currency, availability_checked_at, landing_url, affiliate_url, image_url, image_source, image_rights_status, terms_expiry, last_verified_at.

### Match
post_id, offer_id, relevance_score, intent_type, rationale, confidence, selected_by, status.
Never force an irrelevant offer into an article. Allow no-match.

### Placement
post_id, offer_id, placement_type (in_content / product_card / image_link / CTA), image_attachment_id, affiliate_url, disclosure_text, rel_attributes, inserted_at, verification_status, last_checked_at.

### Event/report
impression where measurable, click (when consent/privacy rules permit), outbound_click_id/sub_id, conversion/commission when provider reports it, provider_report_date, currency, gross_commission, adjustments, net_commission.

## 4. Matching and prioritization
1. Collect eligible published posts from the chosen WordPress site(s).
2. Rank by reliable page views descending only when source, date range and coverage are known. Missing analytics must be marked "not collected", not zero.
3. If reliable views are unavailable, use a clearly labelled fallback: latest published posts, with publication date and no invented ranking.
4. Match by topic, user intent, language, destination and market. Health claims/products require stricter relevance and content-safety checks.
5. Require minimum relevance threshold; route uncertain matches to review queue.
6. Deduplicate repeated offers within a post and prevent duplicate placements on reruns.

## 5. Image handling
- Use provider-supplied image URLs, feeds, APIs or explicitly licensed media only where the affiliate program's terms permit.
- Do not scrape, hotlink, download, re-host or alter product/hotel images unless the provider's terms or license explicitly permit that exact use.
- Store image source, rights basis, retrieval time, attribution requirement and provider item ID.
- Prefer approved product/offer image widgets or linked remote assets when required by provider terms.
- If no compliant image is available, use a neutral text CTA or a separately licensed editorial image; do not fabricate an image of the exact product/property.
- Reuse one approved image asset for the same offer where permitted; do not upload duplicates for every post.
- Preserve existing featured images and article media unless explicitly authorized to replace them.

## 6. Link and disclosure rules
- Only use affiliate URLs generated by the user's approved account, official API/feed, or a user-supplied link explicitly confirmed for that provider.
- Never infer ownership from a URL's appearance.
- Keep the original destination and tracking parameters intact; validate redirect and destination before placement.
- Add clear Korean/locale-appropriate affiliate disclosure near the placement, e.g. "이 글에는 제휴 링크가 포함되어 있으며, 링크를 통해 구매/예약이 발생하면 운영자가 수수료를 받을 수 있습니다." Customize to each program's required wording.
- Apply appropriate rel attributes (sponsored and nofollow where applicable) and safe target behavior.
- Do not claim a click/order/commission unless confirmed by provider reporting.

## 7. WordPress publishing architecture
- Provider-independent core service: content collector, offer catalog, matcher, placement renderer, batch executor, verifier, report exporter.
- WordPress connector: REST API using least-privilege Application Password or supported OAuth; no credentials committed to Git.
- Use server-side batch jobs with resumable checkpoints, idempotency keys, bounded batches and per-post receipts.
- Default to dry-run. Then apply to a small pilot batch, verify rendered HTML and links, and only then scale.
- Never overwrite existing content wholesale. Insert a clearly marked managed affiliate block at a safe insertion point; preserve all original text, images, metadata and status.
- Add a stable marker/placement ID to each managed block so reruns update rather than duplicate.
- Retry only transient failures with capped backoff. Continue other posts when one fails.
- Support rollback by placement ID, without deleting or modifying unrelated content.

## 8. Batch workflow
A. Discover site and eligible posts.
B. Import provider offer catalog / approved links.
C. Generate ranked post-to-offer match table.
D. Generate dry-run preview including image-rights and link-ownership status.
E. Pilot 3–5 posts.
F. Verify post HTML, image render, destination, disclosure and rel attributes.
G. Execute remaining posts in bounded batches.
H. Export CSV/Markdown URL matrix and per-post success/failure reasons to GitHub.
I. Reconcile clicks and commissions from provider reports.

## 9. Initial rollout
Phase 0 — configuration and credentials:
- Register Coupang, Trip.com and Agoda adapters as providers.
- Keep each approval status "unknown" until verified.
- Add provider-specific terms, image policy, tracking IDs and credentials as environment secrets.
- Do not put secrets, account email, partner IDs or private dashboard exports in this public repository.

Phase 1 — K-Health365 pilot:
- Use the existing confirmed Coupang Omega-3 link only for relevant Omega-3/cardiovascular-intent articles.
- Other health offers require their own verified product and account-generated affiliate links.
- Do not claim 100 placements are ready until offers and compliant images exist.

Phase 2 — K-Trip365 travel pilot:
- Add Trip.com and Agoda accommodation/travel offers after account approval and tracking-link validation.
- Match destination-specific hotel/travel content to relevant offers.
- Do not show live price or availability unless refreshed from a permitted source and timestamped.

Phase 3 — portfolio expansion:
- Add other WordPress properties and providers through configuration, not custom one-off code.
- Use site/category/provider allowlists and per-site rollout limits.

## 10. Reporting
Every run must produce:
- selected posts and ranking basis/date range
- provider, offer, item ID, affiliate URL (mask secrets; tracking URL may be shown only if safe)
- image URL/source/rights status
- placement status: planned / inserted / verified / failed / skipped
- post permalink, HTTP result, timestamp and error
- clicks/orders/commission only when provider-reported
- total attempted, inserted, verified, skipped and failed counts.

## 11. Security, compliance and cost
- Store API keys and WordPress credentials only in GitHub Actions/VPS secret storage.
- Never commit .env, cookies, Application Passwords, partner credentials or private reports.
- Respect provider terms, API rate limits, robots/access restrictions, privacy and local advertising/disclosure laws.
- No new paid SaaS/API without explicit cost approval. Prefer official free affiliate feeds/APIs and user-supplied tracking links where permitted.
- Health content must not imply supplements treat or prevent disease without reliable authorization/evidence; preserve editorial integrity and AdSense trust.

## 12. Acceptance criteria
- One common schema supports Coupang, Trip.com and Agoda without provider-specific changes to the batch workflow.
- Provider status and link ownership are explicit and verifiable.
- Image rights are checked before upload or display.
- Dry-run preview and 3–5-post pilot pass before bulk execution.
- Reruns are idempotent; existing content is preserved.
- Per-post outcomes and final URL matrix are exported.
- No credentials or secrets appear in repository history.

## 13. Current status
This document defines the architecture only. It does not mean code has been implemented, affiliate accounts connected, offers imported, images cleared for use, or WordPress posts modified. Those steps require connector/API implementation, provider account verification and a controlled pilot.
