# 통제실 운영 상태와 RSS 감시 — 2026-09-09

사용자 확정: 일반 WordPress 25개, 뉴스룸 2개, 현재 표시되는 Blogspot 전체, Tistory 5개를 사이트별로 추적한다. 뉴스룸은 새 RSS 기사가 실행 조건이며 하루 10회 예약이나 일일 발행 상한을 두지 않는다.

## 상태를 판정하는 근거

| 화면 | 실제 근거 |
|---|---|
| 요청 접수 | SQLite에 요청·대상 사이트 저장. GitHub 전달/대기 상태를 별도 문구로 표시 |
| 작업 중 | 요청 응답으로 받은 정확한 GitHub 실행 ID 및 실행 단계 |
| 검토 준비 | Tistory의 정확한 `site_id:request_id` 대기열 행과 제목·본문 확인 |
| 게시 중 | WordPress API 호출 직전의 실행 체크포인트 또는 Blogger의 정확한 후속 게시 실행 |
| 게시 완료 | 해당 사이트/작업의 공개 페이지 검증 체크포인트·게시 결과 파일·게시 대기열의 공개 URL |
| 중단 / 실패 | 실행 서버의 중단·실패 결론 및 단계/기사 검수 오류 |
| 확인 필요 | 실행 종료 후 게시 증거 없음, 전달 결과 불명확, 게시 검증 실패 |

실행 성공(exit code 0)만으로 게시 완료를 표시하지 않는다. 통신 장애는 게시 실패로 단정하지 않는다. 오래된 상태에는 마지막 확인 시각과 연결 지연을 표시한다. GitHub 실시간 체크포인트 권한이 없으면 관찰 가능한 실행 단계로 대체하고 완료는 결과 자료로 재확인한다.

## VPS 설치 및 전환

1. 실제 `korea365-control.service`의 `User`, `Group`, `WorkingDirectory`, `EnvironmentFile`을 확인한다. 운영 VPS가 `root`와 `/etc/korea365/control.env`를 쓰는 경우 저장소의 일반 예시(`korea365`, `/etc/korea365/control-center.env`)로 덮어쓰지 않는다.
2. 웹 서비스와 새 `korea365-operations.service`가 **동일 사용자·동일 환경파일·동일 DB 경로**를 사용하도록 새 서비스 파일을 조정한다. 기존 서비스 정의는 유지한다.
3. 공통 환경에 `CONTROL_CENTER_GITHUB_REPO`, `CONTROL_CENTER_GITHUB_TOKEN`, `CONTROL_OPERATIONS_DB=/opt/korea365/data/control-operations.sqlite3`를 설정한다. 토큰은 해당 저장소 Actions 실행·조회·결과 아티팩트 조회와 Checks 조회 권한이 필요하다. 값은 로그에 출력하지 않는다.
4. 저장소 변경과 Python 의존성을 준비한 다음 웹 서비스를 재시작하고 상태 감시 서비스를 활성화한다. 서비스에는 `Restart=always`, 프로세스 간 SQLite 잠금과 작업 임대가 적용된다.
5. GitHub 뉴스룸 고정 예약 삭제와 VPS 감시 시작을 같은 전환 작업으로 처리한다. 새 뉴스룸 workflow가 기본 브랜치에 있어야 `source_url` 입력을 받을 수 있다. VPS가 준비되기 전에 예약만 제거하고 전환 완료로 보고하지 않는다.
6. `/api/operations`에서 실제 요청 번호, 상태 및 RSS 매체별 최근 확인 시각을 확인한다. 먼저 읽기 검증을 하고, 운영 요청은 실제 발행을 수반한다는 점을 구분한다.
7. 서비스 재시작 후 이전 요청이 다시 발행되지 않고 같은 실행 ID를 계속 추적하는지 확인한다. 일일 DB 백업은 SQLite backup API로 수행하고 WAL 파일을 분리 복사하지 않는다. 새 VPS로 옮길 때 이 DB도 보존한다.

기존 `CONTROL_CENTER_SECRET_KEY`와 `CONTROL_CENTER_CSRF` 환경값이 있으면 유지한다. 없을 경우 DB에 공통 값을 저장해 여러 웹 프로세스·재시작 사이의 요청 확인값 불일치를 방지한다.

## 뉴스룸 감시

- `config/newsroom_rss_watch.json`이 매체와 확인 주기를 정의한다. 확인 주기는 발행 횟수가 아니다.
- 첫 정상 RSS 읽기는 기존 기사 기준점을 저장한다. 다음 읽기부터 새 URL만 처리한다. 기사 URL+뉴스룸으로 중복 방지 키를 만든다.
- 대기 기사와 요청 기록은 VPS DB에 남는다. 한 사이트에 미완료 작업이 있으면 다음 기사는 대기한다. 모호한 실행 결과는 임의로 재실행하지 않는다.
- URL을 `newsrooms-daily-publisher.yml`에 전달하고 작성기가 현재 RSS에서 그 기사만 다시 확인한다. 다른 기사로 대체하지 않는다.
- 게시 체크포인트 전송 실패는 기사 게시 재시도의 원인이 되지 않는다.
- 원문 기사 검수 실패는 상태 표시 개선만으로 해결되지 않는다. 실제 최근 실패에서 출처 검증·검수 문제가 확인됐으며 해당 사유를 운영 카드에 표시한다.

## 배포 전 확인된 제한

- 현재 화면은 Blogspot 등록 33개 중 중복 테스트 블로그 1개를 제외한 32개를 표시한다. 이 변경은 제외 정책을 임의로 뒤집지 않는다.
- 로컬 RSS 연결 확인에서 조선일보·동아일보·뉴욕타임스는 응답했다. 한겨레는 HTTP 403, CNN은 TLS 연결 오류로 VPS에서도 매체별 상태 확인이 필요하다. 오류를 우회하거나 정상으로 표시하지 않는다.
- Tistory의 검토·승인 화면은 기존 로그인된 등록기로 이어진다. 클라우드에서 즉시 공개 게시됐다고 표시하지 않는다.
- 코드·모의 작업 검증과 실제 운영 배포/실제 발행 검증은 별도로 보고한다.
