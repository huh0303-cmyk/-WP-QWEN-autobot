# KOREA365 PM LOCK — 2026-09-29

This document is the operating lock for the Korea365 control apps and the London Project. It is the PM source of truth. Agents may repair or extend this architecture, but must not create competing dashboards, schedulers, article pipelines, ranking definitions, or data stores.

## 1. Product split

- `control.korea365.org`: CEO/PM dashboard only. The blog fleet is displayed as one compact Excel-like table, one site per row. No blog cards on Control.
- `blog.korea365.org`: detailed blog operations app for WordPress, newsrooms, Blogspot, Naver and Tistory.
- `youtube.korea365.org`: all YouTube operations.
- `sns.korea365.org`: Instagram, Threads, TikTok, Facebook and future SNS operations.
- Every app must show persistent CONTROL / BLOG / YOUTUBE / SNS cross-links.
- Keep one shared repository, shared auth/data contracts and shared VPS. Subdomains are presentation/service boundaries, not four independent projects.

## 2. Blog fleet and daily writing-priority rank

Exactly 68 blog properties are in one mixed ranking:
- WordPress general: 25
- WordPress newsrooms: 2
- Blogspot: 33
- Naver: 3
- Tistory: 5
- Total: 68

There is no platform-specific ranking. WP, NEWS, BLOGSPOT, NAVER and TISTORY are mixed together. Platform is only a badge/column.

Ranking definition: previous KST calendar day's confirmed visitor count, descending. The ranking is recalculated every day and is the default daily writing-priority order. Display ranks as `1위`, `2위`, ... `68위`.

## 3. Required metrics per blog row

Every row exposes these four core metrics:
1. 어제 방문자수 (증감 = 어제 - 그제)
2. 총 방문자수 (증감)
3. 총 콘텐츠수 (증감)
4. Google 색인 글수 (증감; GSC / URL Inspection verified when technically possible)

Never coerce unavailable data to zero. Never rank a missing measurement as a real zero. Missing/stale data is a connector failure to repair, not a permanent UI state.
## 4. Data-source rules

- WordPress visitor metrics: public `/wp-json/site-stats/v1/visitors` counter. It must provide today, yesterday, day-before-yesterday and total.
- Naver visitor metrics: use the public `NVisitorgp4Ajax.naver?blogId=<id>` daily visitor XML where available. Do not declare Naver visitor counts impossible while this endpoint works.
- Tistory visitor metrics: use the public skin visitor counter when rendered. If a skin hides it, repair/replace the connector rather than invent data.
- Blogspot visitor metrics: use a current authoritative source with daily history. Do not use frozen historical snapshots as if current.
- Content counts must come from the platform/publication inventory, not inferred from scheduler logs.
- Google indexed counts must come from GSC / URL Inspection evidence where technically supported. Search result estimates are not a substitute.
- Every metric must carry freshness/check time and connector status.

## 5. Control display lock

The Control blog fleet is a spreadsheet-style table, not cards.

Columns:
`순위 | 플랫폼 | 사이트 | 어제 방문자(증감) | 총 방문자(증감) | 총 콘텐츠(증감) | Google 색인(증감) | 데이터 상태 | 확인시각`

Requirements:
- one site per row;
- exactly 68 rows;
- backend ranking order is authoritative;
- sticky table header;
- compact row height;
- positive delta green, negative delta red;
- 5-minute UI refresh without changing the day's ranking definition;
- CSV download from the same API contract;
- clicking a site opens the real site.

## 6. Publishing architecture lock

The existing London Project n8n 4-Agent pipeline remains the article workflow source of truth. Do not create a second competing article pipeline or duplicate scheduler.

Visible stages remain:
Research -> Writer -> Image -> Publisher/Verify -> Receipt.

A failure is isolated by stage and must not stop unrelated sites. Existing legacy schedulers are migrated only after canary success and with rollback available.

Writer provider order is:
Gemini free-tier model chain (multiple configured free models) -> GPT-5-mini bounded fallback -> local Ollama/Qwen fallback.

A paid provider being unavailable must not stop the fleet when an allowed free/local fallback exists. No new paid service or spend increase without explicit owner approval.

## 7. Agent ownership

- GPT PM: architecture owner, source-of-truth keeper, integration reviewer, deployment gate, acceptance testing, conflict resolution and final merge to main.
- Claude: backend/data connectors, metrics integrity, tests, failure analysis. No competing UI or pipeline.
- Gemini: frontend/UI, lightweight display, mobile usability and visual consistency. No backend data semantics or competing pipeline.
- Other coding agents may assist only inside the PM-defined scope and must work on isolated branches/worktrees.

Agents never push directly to main. GPT PM reviews and merges.

## 8. Acceptance gates

A change is not complete because code exists. Completion requires:
- focused tests pass;
- exact fleet count and platform counts match the lock;
- measured data freshness is visible;
- no fake zeros;
- no duplicate pipelines/schedulers;
- production deploy succeeds;
- final production URL/API is checked after deploy.

This file supersedes ad-hoc dashboard/ranking interpretations that conflict with these rules.
